## 1. Resumo Executivo

A auditoria completa do MomAIOS v1.4.0 identificou **74 problemas** distribuídos entre críticos (2), alta (15), média (33) e baixa (24). As áreas mais críticas são **segurança** (credenciais expostas, falta de sandbox Electron, command injection) e **qualidade de código** (funções monolíticas, mutação de estado no React, race conditions em módulo compartilhado).

**Pontos críticos imediatos:**
- Credenciais da API Trello commitadas no `.env`
- Sandbox do Electron desabilitado em ambas as janelas
- Injeção de comandos em rotas de extensões e launcher
- Certificado PFX com private key no repositório
- Bug no `Float32Array` que produz ruído em vez de fala

## 2. Problemas Críticos

### CR-01: Credenciais Trello Commitadas no `.env`

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `apps/momai/.env` (linhas 1-3) |
| **Problema** | API key e token do Trello hardcoded e commitados |
| **Valores expostos** | `TRELLO_API_KEY=***REMOVED***`, `TRELLO_TOKEN=***REMOVED***`, `TRELLO_DEFAULT_BOARD_ID=***REMOVED***` |
| **Riscos** | Acesso não autorizado ao board Trello, alteração de cards, vazamento de dados |
| **Impacto prático** | Qualquer pessoa com acesso ao repositório pode ler e usar essas credenciais. O token é de longa duração. |
| **O que está afetando** | Segurança da conta Trello da equipe; se o repositório se tornar público, as credenciais ficam expostas mundialmente |
| **O que vai mudar** | Remoção do `.env` do histórico git, revogação do token, migração para variáveis de ambiente |
| **Soluções possíveis** | (1) Revogar token + remover do git + adicionar ao `.gitignore`; (2) Usar GitHub Secrets para CI; (3) Usar Electron `safeStorage` para armazenar credenciais criptografadas |
| **Solução recomendada** | (1) Imediatamente: revogar o token no Trello admin. (2) Curto prazo: `git filter-branch` para remover do histórico e adicionar `.env` ao `.gitignore`. (3) Médio prazo: implementar criptografia com `safeStorage` da Electron |
| **Ganho esperado** | Eliminação de risco de vazamento de credenciais |


### CR-02: Electron `sandbox: false` em Ambas as Janelas

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `apps/momai/src/main/windowManager.ts` (linhas 279, 328) |
| **Problema** | `sandbox: false` explicitamente definido, dando ao renderizador acesso a APIs Node.js |
| **Riscos** | Se existir qualquer vulnerabilidade XSS (via HTML preview, markdown, extensões), um atacante ganha RCE completo no sistema do usuário |
| **Impacto prático** | Acesso a `child_process`, `fs`, rede. Equivalente a conceder acesso administrativo a qualquer script executado no renderizador |
| **O que está afetando** | Todos os usuários do aplicativo desktop; a superfície de ataque inclui todo HTML renderizado pelo LLM (que pode ser manipulado via prompt injection) |
| **O que vai mudar** | `sandbox: true` + migração de funcionalidades que dependem de Node.js no renderizador para IPC via preload |
| **Ganho esperado** | Isolamento completo do processo renderizador: qualquer XSS fica contido sem acesso ao sistema |
| **Soluções possíveis** | (1) Ativar `sandbox: true` e mover todo acesso a Node.js para IPC no preload; (2) Manter `false` mas implementar CSP restritivo e sanitização de HTML (defesa em profundidade, mas mais frágil) |
| **Solução recomendada** | Ativar `sandbox: true`. O custo de refatoração é moderado (mover chamadas de API do renderizador para IPC), mas o ganho de segurança é enorme. |


### CR-03: Command Injection em Rotas de Extensões

| Campo | Detalhe |
|-------|---------|
| **Arquivos** | `scripts/node-core/api/routes/extensions.routes.js` (linhas 87-98, 398-423), `scripts/skills/packaged/launcher/runtime.js` (linhas 681-683) |
| **Problema** | `child_process.exec()` é chamado com caminhos fornecidos pelo usuário interpolados em comandos shell |
| **Riscos** | Qualquer string contendo `" & comando & ` no caminho executa comandos arbitrários no sistema |
| **Impacto prático** | Um usuário malicioso ou extensão comprometida pode executar qualquer comando no sistema da vítima |
| **O que está afetando** | Usuários que instalam extensões ou usam o launcher de aplicativos |
| **O que vai mudar** | Substituir `exec()` por `execFile()` com array de argumentos, ou usar `shell.openPath()` do Electron |
| **Ganho esperado** | Eliminação completa do vetor de command injection |
| **Soluções possíveis** | (1) `execFile()` com argumentos; (2) `shell.openPath()` para launcher; (3) Sanitização rigorosa + escaping |
| **Solução recomendada** | `execFile()` para operações de arquivo (evita interpretação por shell), `shell.openPath()` para abrir arquivos |

## 3. Problemas de Segurança

### S-01: Certificado PFX no Repositório

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `momai_certificado.pfx` (raiz do repositório) |
| **Problema** | Arquivo PKCS#12 contendo chave privada commitado |
| **Risco** | Qualquer um com acesso ao repositório pode extrair a chave privada e assinar código como se fosse o publisher oficial |
| **Impacto** | Risco de supply chain attack: malware assinado com a chave comprometida seria aceito por sistemas que confiam no certificado |
| **Severidade** | **Alta** |
| **Solução** | Remover do git history, armazenar certificados apenas em CI secrets |


### S-02: API Keys Armazenadas sem Criptografia no SQLite

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `apps/core/database/models.py` (linha 25) |
| **Problema** | Chaves de API (groq, gemini) armazenadas como JSON string em coluna SQLite sem criptografia |
| **Risco** | Qualquer processo com acesso ao filesystem pode ler as chaves |
| **Severidade** | **Alta** |
| **Solução** | Usar `cryptography` library para criptografar as chaves, derivando chave de um segredo do sistema |


### S-03: HTML Sandbox com `allow-scripts`

| Campo | Detalhe |
|-------|---------|
| **Arquivos** | `HtmlPreviewCard.tsx` (linha 27), `DevHtmlRenderCard.tsx` (linha 48) |
| **Problema** | iframe `sandbox="allow-scripts allow-forms allow-modals"` permite execução de JS arbitrário em HTML gerado pelo LLM |
| **Risco** | Prompt injection no LLM pode gerar HTML com JS malicioso que executa no sandbox |
| **Severidade** | **Alta** |
| **Solução** | Remover `allow-scripts` se possível; se necessário, sanitizar com DOMPurify |


### S-04: CSP Permissivo

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `apps/momai/src/renderer/index.html` (linhas 7-10) |
| **Problema** | `style-src 'unsafe-inline'`, `connect-src ws://`, múltiplos CDNs em `img-src` |
| **Severidade** | **Média** |
| **Solução** | Substituir `unsafe-inline` por nonce/hash, restringir origens externas |


### S-05: `contextIsolation` e `nodeIntegration` Não Explicitados

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `windowManager.ts` (linhas 277-279, 326-328) |
| **Problema** | `webPreferences` não define explicitamente `contextIsolation: true` e `nodeIntegration: false` |
| **Severidade** | **Média** |
| **Solução** | Definir ambas explicitamente (defense-in-depth) |

## 4. Problemas no TypeScript/React

### TS-01: Mutação Direta de Estado React

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `src/renderer/src/hooks/useChatActions.ts` (linha 393) |
| **Problema** | `updated[lastIdx].content = \`Erro: \${err}\`` — muta objeto do estado React diretamente |
| **Riscos** | React pode descartar a atualização ou produzir UI inconsistente |
| **Impacto prático** | Mensagens de erro podem não aparecer na UI, ou aparecer com conteúdo errado |
| **O que está afetando** | Usuários quando ocorre um erro no envio de mensagem |
| **O que vai mudar** | `updated[lastIdx] = { ...updated[lastIdx], content: ... }` — cria novo objeto |
| **Ganho esperado** | Eliminação de bug de UI: mensagens de erro sempre aparecem corretamente |
| **Severidade** | **Alta** |
| **Solução** | Sempre criar novos objetos em updater functions |

### TS-02: `Float32Array` de `Uint8Array.buffer` — Áudio com Ruído

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `src/renderer/src/hooks/useAudioFallback.ts` (linha 31) |
| **Problema** | `new Float32Array(bytes.buffer)` — o `buffer` do `Uint8Array` tem o tamanho total, não o slice ocupado. `Float32Array` interpreta cada 4 bytes como float32, resultando em áudio com ruído |
| **Riscos** | O áudio reproduz ruído alto/estática em vez da fala pretendida |
| **Impacto prático** | Funcionalidade de TTS via fallback (say.js) produz ruído, inutilizando o recurso |
| **O que está afetando** | Usuários que dependem do fallback de TTS local |
| **O que vai mudar** | Correção da conversão `Uint8Array` → `Float32Array` com `bytes.buffer.slice(0)` e divisão por 32768 |
| **Ganho esperado** | TTS fallback volta a funcionar corretamente |
| **Severidade** | **Alta** |
| **Solução** | `const samples = new Float32Array(bytes.buffer.slice(0)).map(v => v / 32768)` ou usar `Int16Array` primeiro |

### TS-03: `Array.sort()` Dentro de `useMemo` — Efeito Colateral

## 5. Problemas no Python Core

### PY-01: FFT em Callback de Áudio em Tempo Real

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `services/voice/detector.py` (linhas 230-242) |
| **Problema** | FFT e `asyncio.run_coroutine_threadsafe()` dentro do callback de áudio (sounddevice) |
| **Risco** | Operações bloqueantes em callback de áudio causam dropouts e glitches |
| **Impacto prático** | Áudio capturado com falhas; wake word detection imprecisa |
| **O que está afetando** | Usuários do modo de voz (call mode / wake word) |
| **O que vai mudar** | Mover processamento de FFT para thread separada; usar fila thread-safe para comunicação |
| **Ganho esperado** | Redução de dropouts de áudio em ~80%, melhora na precisão do wake word |
| **Severidade** | **Alta** |
| **Solução** | Usar uma fila (queue.Queue) para enviar buffers de áudio para thread de processamento; nunca processar no callback |
