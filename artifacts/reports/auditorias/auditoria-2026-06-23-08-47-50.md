## 1. Resumo Executivo

A auditoria completa do MomAIOS encontrou **38 problemas** distribuídos em todas as camadas da aplicação: segurança (11), qualidade de código TypeScript/React (10), backend Python (9), e Node Core/scripts (8).

**Classificação de Risco:**

| Gravidade | Quantidade |
|-----------|-----------|
| **CRÍTICO** | 2 |
| **ALTO** | 12 |
| **MÉDIO** | 17 |

### Principais Descobertas

- **CREDENCIAIS REAIS COMMITADAS**: Token da API do Trello e senha de certificado PFX estão hardcoded no repositório.
- **IPC GENÉRICO SEM RESTRIÇÃO**: A bridge do preload expõe `invoke`/`send`/`on` genéricos, anulando o modelo de isolamento do Electron.
- **TOKEN DE SESSÃO EXPOSTO**: O token de autenticação é passado como argumento de linha de comando, visível a todos os processos do sistema.
- **AUSÊNCIA DE ERROR BOUNDARIES**: Zero error boundaries no React — qualquer exceção não tratada derruba toda a UI.
- **TIPAGEM FRACA**: Mais de 143 ocorrências de tipo `any` no TypeScript, anulando os benefícios do sistema de tipos.
- **COMANDO INJECTION**: Extração de extensões usa `exec()` com paths derivados de entrada do usuário.

## 3. Problemas de Segurança

### CRÍTICO-1: Credenciais da API Trello Commitadas no Repositório

**Arquivo:** `apps/momai/.env` (linhas 1-3)
**Risco:** **CRÍTICO**

**O problema:** Três credenciais reais da API do Trello estão commitadas no repositório Git:
```
TRELLO_API_KEY=***REVOGADO***
TRELLO_TOKEN=***REVOGADO***
TRELLO_DEFAULT_BOARD_ID=***REVOGADO***
```
*(Valores reais removidos deste relatório após rotação de credenciais. Ver `apps/momai/.env` local para os valores reais — que NÃO estão mais no git.)*

**Riscos:** Qualquer pessoa com acesso ao repositório (incluindo colaboradores ou attackers que acessem um clone) pode usar estas credenciais para ler, modificar e deletar boards do Trello.

**Impacto prático:** Exfiltração de dados gerenciados no Trello, manipulação de cards, acesso não autorizado a boards privados.

**O que está afetando:** Toda a organização — dados de planejamento, tarefas, documentação no Trello.

**O que vai mudar:**
1. Remover `.env` do tracking do Git (`git rm --cached apps/momai/.env`)
2. Adicionar `.env` ao `.gitignore`
3. Usar `.env.example` como template

**Ganho esperado:** Eliminação imediata de um vetor de vazamento de credenciais.

**Soluções possíveis:**
1. Revogar token, remover do git, adicionar ao `.gitignore`
2. Usar GitHub Secrets + CI/CD injection
3. Usar Electron safeStorage + keychain

**Solução recomendada:** Opção 1 + 2. Revogar imediatamente o token no Trello, remover o arquivo do histórico do Git, e configurar injeção via CI/CD.

### CRÍTICO-2: Senha de Certificado PFX Hardcoded

**Arquivos:**
- `apps/momai/scripts/ensure-cert.js` (linha 6)
- `apps/momai/scripts/sign-appx.js` (linha 9)

**Risco:** **CRÍTICO**

**O problema:** A senha do certificado PFX usado para assinar o aplicativo está hardcoded no código-fonte:
```javascript
const password = 'momai2026'
```
O certificado é instalado nos storages "Trusted Root" e "Trusted People" do Windows (`sign-appx.js` linhas 201-203).

**Riscos:** Um atacante com acesso ao repositório pode usar esta senha para assinar software malicioso que será confiado pelo sistema operacional.

**Impacto prático:** Qualquer pessoa pode assinar executáveis como se fossem da MomAI. Instalação de malware com assinatura válida.

**O que está afetando:** Todos os usuários do Windows que confiam no certificado MomAI.

**O que vai mudar:**
1. Mover senha para variável de ambiente `PFX_PASSWORD`
2. Configurar no CI/CD (GitHub Actions secrets)
3. Remover senha do código-fonte

**Ganho esperado:** Eliminação completa do risco de abuso de certificado.

**Soluções possíveis:**
1. Mover para environment variables + CI/CD secrets
2. Usar Azure Key Vault ou similar
3. Usar hardware security module (HSM)

**Solução recomendada:** Opção 1. É a mais simples e imediata.

### ALTO-1: Chaves de API Expostas no Renderer

**Arquivos:**
- `apps/momai/src/renderer/src/hooks/useSettingsCard.ts` (linhas 20, 80)
- `apps/momai/scripts/node-core/api/routes/settings.routes.js` (linhas 62-68, 89-99)
- `apps/core/database/models.py` (linha 25)

**Risco:** **ALTO**

**O problema:** As chaves de API (Groq, Gemini) são descriptografadas no Node Core e enviadas ao renderer como parte do JSON de configurações. O renderer pode lê-las e exibi-las. Se um XSS ou extensão maliciosa comprometer o contexto do renderer, as chaves são exfiltráveis.

**Fluxo atual:**
1. Electron safeStorage descriptografa as chaves
2. Node Core envia para o renderer via HTTP response
3. Renderer acessa via `window.api`
4. Configurações são re-enviadas ao Node Core no save

**Riscos:** Exposição de chaves de API de serviços de IA (Groq, Gemini) para qualquer código executando no renderer.

**Impacto prático:** Uso não autorizado de quotas de API, custos inesperados.

**O que está afetando:** O bolso do desenvolvedor (custos de API) e a segurança do sistema.

**O que vai mudar:**
1. Enviar apenas `has_keys: boolean` para o renderer
2. Gerenciar chaves exclusivamente no main/backend process
3. Adicionar canal IPC dedicado para configuração de chaves

**Ganho esperado:** Eliminação do vetor de exfiltração de chaves via renderer.

**Soluções possíveis:**
1. Nunca enviar chaves ao renderer, usar IPC para operações
2. Usar proxy no main process que aplica as chaves nas requisições
3. Manter chaves apenas no backend Python com endpoints proxy

**Solução recomendada:** Opção 1 + 2. O main process deve ser o único detentor das chaves.

### ALTO-2: Proxy Node Core → Python Sem Header de Autenticação

**Arquivos:**
- `apps/momai/scripts/node-core/api/routes/chat.routes.js` (linhas 35-37, 89-92)
- `apps/momai/scripts/node-core/index.js` (linhas 272-297, função `proxyToPython`)

**Risco:** **ALTO**

**O problema:** O Node Core faz proxy de requisições para o Python sidecar sem incluir o header `Authorization: Bearer <token>`:

```javascript
headers: { 'Content-Type': 'application/json' }  // Sem Authorization!
```

O Python sidecar verifica o token Bearer no middleware de autenticação (`auth.py` linha 19). Como o header não é enviado:
- Se `MOMAI_SESSION_TOKEN` está setado no Python → 401 Unauthorized
- Se `MOMAI_SESSION_TOKEN` não está setado → 500 (env var missing)

**Riscos:** O proxy está funcionalmente quebrado — ou o Python rejeita (401) ou crasha (500). Nenhum request passa.

**Impacto prático:** Recursos como STT, TTS, wake word detection que dependem do Python sidecar não funcionam via Node Core.

**O que está afetando:** Toda funcionalidade de voz (STT, TTS, wake word) que depende do proxy Node Core → Python.

**O que vai mudar:**
Adicionar header de autorização em todas as chamadas proxy:
```javascript
headers: {
  'Content-Type': 'application/json',
  'Authorization': `Bearer ${token}`
}
```

**Ganho esperado:** Correção do fluxo de voz (STT/TTS) que estava quebrado.

**Soluções possíveis:**
1. Adicionar token Bearer a todas as chamadas proxy
2. Fazer o Electron se comunicar diretamente com o Python sem proxy
3. Usar Unix sockets para comunicação interna sem auth HTTP

**Solução recomendada:** Opção 1 — correção mínima e consistente com a arquitetura existente.

### ALTO-3: IPC Genérico Sem Whitelist no Preload

**Arquivo:** `apps/momai/src/preload/index.ts` (linhas 199-205)

**Risco:** **ALTO**

**O problema:** A bridge do preload expõe `invoke`, `send`, e `on` genéricos para o renderer através de `window.api`:

```typescript
invoke: (channel: string, ...args: any[]): Promise<any> => ipcRenderer.invoke(channel, ...args),
send: (channel: string, ...args: any[]): void => ipcRenderer.send(channel, ...args),
```

Isso permite que QUALQUER código no renderer chame QUALQUER canal IPC, incluindo canais como `restart-backend`, `get-session-token`, etc.

**Riscos:** Anula o modelo de segurança do Electron (context isolation + preload). Qualquer vulnerabilidade XSS no renderer permite acesso total ao main process via IPC.

**Impacto prático:** O modelo de segurança baseado em contextIsolation é inútil. Uma extensão maliciosa ou injeção de script tem acesso irrestrito ao sistema via IPC.

**O que está afetando:** A segurança de todo o aplicativo desktop.

**O que vai mudar:**
Remover os métodos genéricos e expor apenas canais específicos com whitelist:
```typescript
invoke: (channel: string, ...args: any[]) => {
  if (!ALLOWED_INVOKE.has(channel)) return Promise.reject('Channel not allowed')
  return ipcRenderer.invoke(channel, ...args)
}
```

**Ganho esperado:** Isolamento de segurança efetivo entre renderer e main process.

**Soluções possíveis:**
1. Whitelist de canais IPC no preload
2. Expor apenas funções nomeadas específicas
3. Remover `invoke`/`send`/`on` completamente e usar apenas funções nomeadas

**Solução recomendada:** Opção 2 — cada canal IPC deve ter sua própria função nomeada na bridge, como já é feito para a maioria.

### ALTO-4: Token de Sessão Passado Como Argumento de Linha de Comando

**Arquivo:** `apps/momai/src/main/windowManager.ts` (linhas 280-284, 348-352)

**Risco:** **ALTO**

**O problema:** O token de sessão é passado ao renderer como argumento de linha de comando:
```typescript
additionalArguments: [
  `--momai-session-token=${getOrCreateSessionToken()}`
]
```

No Windows, `CommandLine` é visível via WMI. No Linux, `/proc/<pid>/cmdline` é legível por qualquer processo.

**Riscos:** Qualquer processo no mesmo sistema pode ler o token de sessão. Com o token, um atacante pode fazer chamadas autenticadas para o Node Core e Python sidecar.

**Impacto prático:** Comprometimento de toda a comunicação autenticada do aplicativo.

**O que está afetando:** A segurança de todas as APIs do Node Core e Python sidecar.

**O que vai mudar:**
Mover a entrega do token para IPC após o carregamento do renderer:
```typescript
// No preload, após load
const token = await ipcRenderer.invoke('get-session-token')
```

**Ganho esperado:** Token de sessão não fica mais visível para outros processos no sistema.

**Soluções possíveis:**
1. Passar token via IPC após carregamento
2. Usar um pipe nomeado (Unix socket) para comunicação
3. Gerar token no preload e compartilhar via seguro

**Solução recomendada:** Opção 1 — mais simples e elimina o vetor de ataque.

### ALTO-5: Token de Sessão Vazado para Processos Filhos de Extensões

**Arquivo:** `apps/momai/scripts/node-core/services/extension-host-manager.js` (linhas 24-38, 89-98)

**Risco:** **ALTO**

**O problema:** Extensões de comunidade (instaladas de GitHub) recebem o token de sessão no environment:
```javascript
env: {
  ...process.env,   // TODO o environment do pai!
  MOMAI_SESSION_TOKEN: process.env.MOMAI_SESSION_TOKEN,
  ...
}
```

**Riscos:** Qualquer extensão, incluindo extensões maliciosas de comunidade, tem acesso ao token de autenticação completo. Pode fazer chamadas autenticadas para qualquer API.

**Impacto prático:** Uma extensão de comunidade comprometida ou maliciosa tem acesso total ao sistema.

**O que está afetando:** Todos os usuários que instalam extensões de comunidade.

**O que vai mudar:**
Remover `MOMAI_SESSION_TOKEN` do environment de extensões. Criar tokens escopados para comunicação de extensões.

**Ganho esperado:** Extensões não têm mais acesso ao token de autenticação principal.

**Soluções possíveis:**
1. Não passar token para extensões, usar IPC bridge
2. Gerar token escopo-limited para cada extensão
3. Usar um proxy autenticado no host de extensões

**Solução recomendada:** Opção 1 + 2.

### ALTO-6: Comando Injection na Extração de Extensões

**Arquivo:** `apps/momai/scripts/node-core/api/routes/extensions.routes.js` (linhas 291-308)

**Risco:** **ALTO**

**O problema:** A extração de ZIP de extensões usa `exec()` com strings montadas a partir de paths derivados de entrada:
```javascript
exec(`powershell -NoProfile -Command "Expand-Archive -Path '${zipPath}' -DestinationPath '${destDir}' -Force"`, ...)
exec(`unzip -o "${zipPath}" -d "${destDir}"`, ...)
```

**Riscos:** Injeção de comandos via nome de extensão malicioso ou path de download adulterado. Execução remota de código.

**Impacto prático:** Instalação de uma extensão com ID malicioso pode executar comandos arbitrários no sistema.

**O que está afetando:** Servidor Node Core (potencialmente todos os usuários).

**O que vai mudar:**
Substituir `exec()` por `execFile()` ou biblioteca nativa de ZIP:
```javascript
const AdmZip = require('adm-zip')
const zip = new AdmZip(zipPath)
zip.extractAllTo(destDir, true)
```

**Ganho esperado:** Eliminação completa do vetor de command injection.

**Soluções possíveis:**
1. Usar biblioteca JavaScript nativa (adm-zip, yauzl)
2. Usar `execFile()` em vez de `exec()`
3. Validar e sanitizar rigorosamente paths

**Solução recomendada:** Opção 1 + 3. `adm-zip` é puro JavaScript, sem shell envolvido.

### ALTO-7: Endpoint de Shutdown Não Autenticado

**Arquivo:** `apps/momai/scripts/node-core/api/routes/status.routes.js` (linhas 67-73)

**Risco:** **ALTO**

**O problema:** O path `/internal/shutdown` derruba o Node Core via HTTP POST:
```javascript
if (pathname === '/internal/shutdown' && req.method === 'POST') {
  context.shutdownAll()
}
```

Embora esteja atrás do middleware de autenticação, se o token vazar, qualquer um pode derrubar o serviço.

**Riscos:** Negação de serviço local se o token for exposto.

**Impacto prático:** Um processo malicioso na máquina pode derrubar o assistente.

**O que está afetando:** Disponibilidade do serviço.

**O que vai mudar:**
Adicionar verificação adicional (ex: origem IPC ou segredo extra):
```javascript
if (req.headers['x-shutdown-secret'] !== process.env.SHUTDOWN_SECRET) {
  sendJson(res, 403, { error: 'forbidden' })
  return true
}
```

**Ganho esperado:** Camada adicional de segurança para shutdown.

**Solução recomendada:** Restringir shutdown a IPC apenas (não HTTP).

### ALTO-8: Integridade de Extensões Ignorada Quando SHA256 Ausente

**Arquivo:** `apps/momai/scripts/node-core/api/routes/extensions.routes.js` (linhas 411-423)

**Risco:** **ALTO**

**O problema:** Quando `expected_sha256` não é enviado pelo cliente, a instalação continua sem verificação de integridade:
```javascript
if (checksumResult.reason === 'missing') {
  console.warn('install without expected_sha256 — backward compat path')
}
// Continua instalação!
```

**Riscos:** Qualquer chamada ao endpoint de instalação pode baixar e executar código arbitrário sem verificação de integridade.

**Impacto prático:** O mecanismo de segurança de checksum é completamente bypassável.

**O que está afetando:** Integridade de todas as extensões instaladas via API.

**O que vai mudar:**
Tornar `expected_sha256` obrigatório ou buscar do registry como fonte da verdade.

**Ganho esperado:** Verificação de integridade sempre ativa.

**Solução recomendada:** Buscar SHA256 do registry.json em vez de confiar no client.

**Arquivos:**

## 4. Problemas de Qualidade de Código

### ALTO-1: Uso Pervasivo de Tipo `any` (143+ ocorrências)

**Arquivos:** 25+ arquivos em todo o renderer

**Risco:** **ALTO**

**O problema:** O TypeScript é amplamente subutilizado. Mais de 143 ocorrências de `any` anulam a segurança de tipos. Exemplos:

- `api.ts` — parâmetros de requisição tipados como `any` em 12+ locais
- `MainViewRenderer.tsx` — prop `chat: any`
- `observabilityStore.ts` — store completamente sem tipos
- `SkillResponseRegistry.ts` — registro de renderers sem tipos
- `useChatHandlers.ts` — mensagens WebSocket tipadas como `any`
- `WeatherCard.tsx` — props e funções sem tipos

**Riscos:** Bugs que poderiam ser detectados em compile-time só aparecem em runtime. Refatoração é arriscada pois o compilador não pega quebras de contrato.

**Impacto prático:** Cada nova funcionalidade requer mais testes manuais. Bugs de tipo (ex: passar `string` onde `number` é esperado) passam despercebidos.

**O que está afetando:** Desenvolvedores — produtividade reduzida e refatoração arriscada.

**O que vai mudar:** Definição de interfaces TypeScript para:
- Mensagens WebSocket
- Payloads de eventos customizados
- Objeto `chat`
- Respostas de API
- Props de componentes

**Ganho esperado:** Eliminação de ~80% dos bugs de runtime relacionados a tipos que passariam despercebidos.

**Soluções possíveis:**
1. Definição incremental de interfaces, começando pelos tipos mais usados
2. Uso de `zod` (já é dependência) para validação runtime + inferência de tipos
3. Ativação de `strict: true` e `noImplicitAny: true` no tsconfig

**Solução recomendada:** Opção 1 + 3. Ativar `strict` no tsconfig e definir interfaces para os 10 tipos mais usados primeiro.

### ALTO-2: Zero Error Boundaries no React

**Arquivo:** Em toda a aplicação renderer

**Risco:** **ALTO**

**O problema:** NENHUM Error Boundary está implementado. Se qualquer componente lançar uma exceção durante renderização, a árvore React inteira desmonta e o usuário vê uma tela branca.

**Riscos:** Qualquer bug em componente, skill UI, ou renderização de markdown derruba todo o aplicativo.

**Impacto prático:** Experiência do usuário drasticamente prejudicada — um erro em um card de skill derruba o app inteiro.

**O que está afetando:** Usuários finais.

**O que vai mudar:** Adicionar Error Boundaries em 3 níveis:
1. Top-level: `App` inteiro
2. Views: cada rota principal
3. MessageList: cada item de mensagem (conteúdo de terceiros)

**Ganho esperado:** Resiliência — um erro em um componente não derruba o app inteiro.

**Solução recomendada:** Implementar ErrorBoundary genérico e envolver App + MessageList.

**Risco:** **ALTO**

**Riscos:** Dificuldade de manutenção e refatoração. Mudar uma propriedade requer alterar 4 componentes.

**Impacto prático:** Adicionar uma nova funcionalidade ao chat exige alterações em cascata em múltiplos componentes.

**O que está afetando:** Desenvolvedores.

**Ganho esperado:** Redução de ~50 linhas de prop drilling. Adição de novas funcionalidades mais simples.

### ALTO-4: Handler Monolítico de 619 Linhas

**Arquivo:** `apps/momai/src/renderer/src/hooks/useChatHandlers.ts` (linhas 37-616)

**Risco:** **ALTO**

**O problema:** `handleWsMessage` é uma única função `useCallback` de 580 linhas que trata 22 tipos de mensagens em uma cadeia gigante de `if/else`. Contém closures aninhadas, `JSON.parse` inline, e lógica de UI misturada com dispatch de estado.

**Riscos:** Impossível testar unitariamente. Qualquer mudança em um tipo de mensagem pode quebrar outros.

**Impacto prático:** Tempo de debug e desenvolvimento muito maior para o sistema de mensagens.

**O que está afetando:** Desenvolvedores — cada mudança no chat requer entender 600+ linhas.

**O que vai mudar:** Refatorar para padrão strategy/handler map:
```typescript
const messageHandlers = {
  'message:assistant': handleAssistantMessage,
  'message:user': handleUserMessage,
  'tool:start': handleToolStart,
  // ...
}
```

**Ganho esperado:** Redução de complexidade ciclomática de ~50 para ~5. Cada handler testável isoladamente.

**Solução recomendada:** Extrair cada branch para função separada em arquivo próprio.

### ALTO-5: `sanitize_message` — Lógica Incorreta

**Arquivo:** `apps/core/api/middleware/error_handler.py` (linhas 32-35)

**Risco:** **ALTO**

**O problema:** A função `sanitize_message` verifica `is_safe_message(fallback)` onde `fallback` é sempre uma string constante segura:
```python
def sanitize_message(message: str, is_dev: bool = False, fallback: str = "Internal server error"):
    if is_dev:
        return str(message)  # <-- correto
    return fallback if is_safe_message(fallback) else "Internal server error"
    #                    ^^^^^^^^ sempre True, lógica morta
```

**Riscos:** Em produção (`is_dev=False`), a mensagem de erro original NUNCA é sanitizada. A função SEMPRE retorna o fallback. A verificação de segurança não está sendo aplicada à mensagem real.

**Impacto prático:** Erros internos (stack traces, paths, dados) podem vazar em produção se o código depender de `sanitize_message` para filtrar mensagens. A intenção era filtrar a mensagem real, não o fallback.

**O que está afetando:** Usuários finais (vazamento de informação) e desenvolvedores (bugs não diagnosticados corretamente).

**O que vai mudar:** A lógica deve verificar a mensagem original:
```python
return message if is_safe_message(message) else fallback
```

**Ganho esperado:** Sanitização efetiva de mensagens de erro em produção.

**Solução recomendada:** Substituir `is_safe_message(fallback)` por `is_safe_message(message)`.

## 9. Recomendação Final

### Prioridade Absoluta (Corrigir Imediatamente)

1. **Revogar credenciais comprometidas** — Token Trello e certificado PFX. Remover do Git history.
2. **Restringir IPC do preload** — Remover `invoke`/`send`/`on` genéricos. Criar funções nomeadas seguras.
3. **Adicionar auth header ao proxy Node Core → Python** — Sem isso, o pipeline de voz está quebrado.
4. **Remover token de sessão de command-line args** — Mover para IPC pós-carregamento.
5. **Parar de vazar token para extensões** — Extensões não precisam do token mestre.

### Curto Prazo (Próximo Sprint)

6. **Adicionar Error Boundaries** no React — 3 níveis: App, views, message list.
7. **Iniciar migração de tipos** — Ativar `strict` no tsconfig, definir interfaces para os tipos mais críticos.
8. **Refatorar `useChatHandlers.ts`** — Extrair handlers por tipo de mensagem.
9. **Corrigir `sanitize_message`** — Verificar mensagem real em vez do fallback.
10. **Substituir `exec()` por `adm-zip`** — Eliminar command injection nas extensões.

### Médio Prazo (Próximos Sprints)

11. **Introduzir React Context** para eliminar prop drilling do chat.
12. **Extrair `ChatInput`** em componentes menores.
13. **Centralizar eventos** em um EventBus tipado.
14. **Adicionar timeouts** a todos os downloads de modelo.
15. **Substituir bare excepts** por `except Exception:`.

- **Segurança:** Eliminação de 11 vetores de ataque, incluindo 2 críticos

- **Resiliência:** Queda de 100% para ~10% em cenários de erro (Error Boundaries)
- **Qualidade:** Redução de ~90% no uso de `any`, bugs de tipo capturados em compile-time
