## 2. Resumo Executivo

O MomAIOS é um projeto ambicioso de assistente virtual local-first com arquitetura bem definida (Electron 3-processos + Node Core + Python sidecar). A análise revela **25 problemas de alta prioridade**, concentrados em três áreas:

1. **Segurança**: token de sessão exposto em `process.env`, XSS via `srcDoc` em preview HTML, armazenamento inseguro de credenciais Trello, e ausência de validação em IPC.
2. **Manutenibilidade**: God Objects (`coreManager.ts` com 934 linhas, `ContainerChat.tsx` com 926 linhas, `useChatHandlers.ts` com 619 linhas), dependência circular entre módulos, e mais de 30 `catch {}` vazios no código.
3. **Performance**: I/O síncrono bloqueando event loop do Electron, duplicação de modelos Whisper na memória (potencial OOM), e ausência de `AbortController` em chamadas de streaming.

Pontos fortes identificados: arquitetura de 3 processos bem separada, CSP configurado, Electron security hardening (sandbox, contextIsolation, bloqueio de webview/devtools), e padrão atômico de escrita em store (temp+rename).

## 3. Problemas por Categoria

### 3.1 Arquitetura & Estrutura do Projeto

#### P001 — `coreManager.ts` é um God Object (934 linhas)

**Arquivo:** `apps/momai/src/main/coreManager.ts`
**Risco:** ALTA
**Problema:** Um único arquivo gerencia: spawn de Node Core, lifecycle do Python sidecar, economia, bridge TTS, dedup de logs, estratégias de kill, e decisões de startup.
**Impacto prático:** Qualquer mudança em subprocesso requer modificar esse arquivo gigante, aumentando risco de regressão.
**Afeta:** Desenvolvedores — manutenção é lenta e arriscada.
**O que vai mudar:** Extrair para `node-core-launcher.ts`, `economy-lifecycle.ts`, `tts-bridge.ts`, `port-utils.ts`, `startup-decision.ts`.
**Ganho esperado:** Reduz complexidade ciclomática de ~60 para ~10 por módulo.
**Soluções possíveis:**
1. Extrair por domínio (recomendado)
2. Manter como está com mais comentários
3. Refatorar usando padrão Mediator
**Solução recomendada:** Opção 1 — separação por responsabilidade única.

#### P002 — Dependência circular entre `coreManager.ts` e `windowManager.ts`

**Arquivos:** `apps/momai/src/main/coreManager.ts` e `windowManager.ts`
**Risco:** ALTA
**Problema:** `windowManager` importa `restartCoreBackend` de `coreManager`, e `coreManager` importa `broadcastEconomyState` de `windowManager`. Dependência circular em nível de módulo.
**Impacto prático:** Se a ordem de avaliação dos módulos mudar (refatoração, bundler, etc.), o import resolve como `undefined`, causando `TypeError: ... is not a function`.
**Afeta:** Desenvolvedores — bugs intermitentes e difíceis de depurar.
**O que vai mudar:** Criar um módulo compartilhado (`shared-events.ts`) ou injetar as dependências via callback.
**Ganho esperado:** Elimina fragile import order dependency.

#### P003 — `ContainerChat.tsx` com 19 `useEffect` hooks e 926 linhas

**Arquivo:** `apps/momai/src/renderer/src/components/ContainerChat.tsx`
**Risco:** ALTA
**Problema:** Um único componente contém `CallModeContent` (~330 linhas com animação canvas), `ContextUsageRing`, e múltiplos concerns de estado — 19 `useEffect` hooks dificultam rastrear ordem de inicialização.
**Impacto prático:** Bugs sutis de stale closure e timing; difícil adicionar nova funcionalidade sem quebrar existente.
**Afeta:** Desenvolvedores — produtividade reduzida em ~40% para mudanças no chat.
**O que vai mudar:** Extrair `CallModeContent` para arquivo próprio; separar hooks por domínio.
**Ganho esperado:** Reduz complexidade do componente principal em ~60%.

#### P004 — `useChatHandlers.ts` com handler monolítico de 580 linhas

**Arquivo:** `apps/momai/src/renderer/src/hooks/useChatHandlers.ts`
**Risco:** ALTA
**Problema:** Um único `useCallback` de 580 linhas trata ~25 tipos de mensagens em if-else aninhados.
**Impacto prático:** Qualquer novo tipo de mensagem requer adicionar mais um branch no if gigante. Testar cobertura de todos os paths é inviável.
**Afeta:** Desenvolvedores.
**O que vai mudar:** Implementar padrão registry/handler (Map<string, HandlerFunction>).
**Ganho esperado:** Reduz handler principal de 580 linhas para ~30 (roteamento).

#### P005 — Cópia orfanada de `scripts/node-core/` na raiz

**Arquivo:** `scripts/node-core/` (raiz do monorepo)
**Risco:** MÉDIA
**Problema:** Diretório com ~9 arquivos de versão antiga/parcial do Node Core, enquanto o ativo está em `apps/momai/scripts/node-core/` (81 arquivos). Pode causar confusão e imports equivocados.
**Impacto prático:** Desenvolvedores podem acidentalmente importar código desatualizado.
**O que vai mudar:** Remover `scripts/node-core/` da raiz.
**Ganho esperado:** Elimina ambiguidade.

#### P006 — Código duplicado de `isPortReachable` em dois arquivos

**Arquivos:** `apps/momai/src/main/coreManager.ts` (linhas 209-224) e `bootstrap/index.ts` (103-118)
**Risco:** ALTA
**Problema:** Lógica idêntica de verificação de porta TCP duplicada. Correções de bug precisam ser aplicadas em dois lugares.
**Impacto prático:** Risco de uma correção ser aplicada em só um lugar.
**O que vai mudar:** Extrair para `port-utils.ts` compartilhado.
**Ganho esperado:** Manutenibilidade — uma única fonte de verdade.

### 3.2 Segurança

#### S001 — Token de sessão exposto em `process.env` e herdado por subprocessos

**Arquivo:** `apps/momai/src/main/index.ts` (linha 252)
**Risco:** ALTA
**Problema:** `MOMAI_SESSION_TOKEN` é setado em `process.env`, que é herdado por child processes (Node Core, Python, extensões). Crash dumps, logs de erro, e processos filho comprometidos podem ler o token.
**Impacto prático:** Um atacante com acesso ao sistema pode extrair o token e autenticar requisições à API.
**Afeta:** Usuários finais — risco de sequestro de sessão.
**O que vai mudar:** Passar token via argumento de linha de comando ou pipe anônimo, não via env var.
**Ganho esperado:** Elimina vazamento de token para subprocessos.

#### S002 — Extensões herdam `process.env` com token de sessão

**Arquivo:** `apps/momai/scripts/node-core/services/extension-host-manager.js` (linha 89)
**Risco:** ALTA
**Problema:** `startPersistent()` spawna child process com `env: { ...process.env, ... }`, passando `MOMAI_SESSION_TOKEN` para toda extensão instalada. Uma extensão maliciosa pode exfiltrar o token.
**Impacto prático:** Qualquer extensão tem acesso irrestrito à API do Node Core.
**Afeta:** Usuários finais — quebra do modelo de segurança de extensões.
**O que vai mudar:** Filtrar env vars passadas para extensões (whitelist de vars seguras).
**Ganho esperado:** Isolamento real entre extensão e core da aplicação.

#### S003 — Path traversal no storage API de extensões

**Arquivo:** `apps/momai/scripts/node-core/services/extension-host-worker.js` (linhas 25-41)
**Risco:** ALTA
**Problema:** `storage.get(key)` faz `path.join(storageBase, \`${key}.json\`)` sem sanitizar `key`. Uma extensão passando `../../store` como key pode ler/escrever qualquer arquivo no `DATA_DIR`.
**Impacto prático:** Extensão pode sobrescrever `messages.json`, `store.json`, ou dados de outras extensões.
**Afeta:** Usuários finais — corrupção de dados.
**O que vai mudar:** Validar `key` com regex (apenas alfanumérico + underscore) ou rejeitar caminhos com `..` ou `/`.
**Ganho esperado:** Elimina vetor de ataque.

#### S004 — XSS via `srcDoc` em preview HTML

**Arquivos:** `HtmlPreviewCard.tsx` (linha 26), `DevHtmlRenderCard.tsx` (linha 47)
**Risco:** ALTA
**Problema:** HTML gerado pelo LLM é renderizado em `iframe srcDoc` com `sandbox="allow-scripts"`. Se o backend for comprometido, código arbitrário executa no contexto do renderer.
**Impacto prático:** Potencial comprometimento total do Electron renderer via LLM manipulado.
**Afeta:** Usuários finais.
**O que vai mudar:** Sanitizar HTML com DOMPurify antes de passar para `srcDoc`.
**Ganho esperado:** Elimina risco de XSS.

#### S005 — Credenciais Trello em plaintext no `.env`

**Arquivo:** `apps/momai/.env` (linhas 1-3)
**Risco:** ALTA
**Problema:** `TRELLO_API_KEY`, `TRELLO_TOKEN`, `TRELLO_DEFAULT_BOARD_ID` armazenadas em texto plano. Atualmente gitignored, mas vulneráveis a backup, exfiltração por extensão, ou erro humano (`git add -f`).
**Impacto prático:** Vazamento daria acesso completo ao board Trello do projeto.
**Afeta:** Organização.
**O que vai mudar:** Rotacionar credenciais; armazenar via Electron `safeStorage` ou gerenciador de senhas do SO.
**Ganho esperado:** Elimina risco de vazamento.

#### S006 — Token em query parameter do WebSocket

**Arquivos:** `useChatWebSocket.ts` (linhas 66-69), `ws-auth.js` (linhas 2-4), `auth.py` (linhas 23-36)
**Risco:** MÉDIA
**Problema:** O token de sessão é passado como `?token=...` na URL de upgrade WebSocket. Query params são logados por proxies, servidores, e visíveis em `Referer` headers.
**Impacto prático:** Token pode vazar para logs de acesso ou extensões de browser.
**Afeta:** Usuários finais.
**O que vai mudar:** Mover token para header `Authorization: Bearer` no upgrade request (WebSocket suporta via protocolo nativo).
**Ganho esperado:** Elimina vazamento via URL.

#### S007 — Mensagens IPC sem tipo (cast para `any`)

**Arquivo:** `apps/momai/src/main/coreManager.ts` (linhas 420, 478)
**Risco:** ALTA
**Problema:** Todas as mensagens entre Node Core e Electron são tratadas via `(raw as any)`. Sem validação de schema, mensagens malformadas podem causar comportamento indefinido.
**Impacto prático:** Crash ou comportamento inesperado por mensagem malformada.
**Afeta:** Usuários finais — instabilidade.
**O que vai mudar:** Definir discriminated union `NodeCoreMessage` com tipos para cada mensagem.
**Ganho esperado:** Type safety na comunicação inter-processos.

### 3.3 Electron / Main Process

#### M001 — `catch {}` vazios em massa (30+ ocorrências)

**Arquivos:** Múltiplos — `coreManager.ts`, `backend-manager.ts`, `bootstrap/index.ts`, `economyScanner.ts`, etc.
**Risco:** ALTA
**Problema:** Blocos `catch {}` silenciosamente engolem erros em shutdown, scans de economia, operações de arquivo, e gerenciamento de subprocessos.
**Impacto prático:** Erros críticos são invisíveis. Debugging de produção é impossível.
**Afeta:** Desenvolvedores — impossibilidade de diagnosticar falhas.
**O que vai mudar:** Adicionar log (`warn`/`error`) em todos os `catch {}` vazios.
**Ganho esperado:** Visibilidade completa de erros.

#### M002 — I/O síncrono em IPC handlers bloqueia event loop

**Arquivo:** `lexical-search.ts` (linhas 69-75)
**Risco:** ALTA
**Problema:** `runLexicalNoteSearch` usa `readFileSync` para ler cada nota. IPC handlers rodam no main process — cada leitura síncrona bloqueia a UI.
**Impacto prático:** UI congela durante busca textual. Com muitas notas, freeze visível de 1-3 segundos.
**Afeta:** Usuários finais — experiência de busca travada.
**O que vai mudar:** Substituir `readFileSync` por `fs.promises.readFile` com concorrência limitada.
**Ganho esperado:** UI responsiva durante buscas (elimina freeze de ~3s).

#### M003 — Índice completo lido/escrito em toda operação de notas

**Arquivo:** `notesService.ts`
**Risco:** ALTA
**Problema:** Toda operação (listar, criar, atualizar, deletar, buscar) lê o JSON inteiro do índice. Operações de escrita salvam o arquivo completo.
**Impacto prático:** O(n) I/O em cada operação, piorando com o crescimento.
**Afeta:** Usuários finais — lentidão progressiva com muitas notas.
**O que vai mudar:** Implementar cache em memória com persistência diferida (debounce) ou usar banco de dados (SQLite/LMDB).
**Ganho esperado:** Operações O(1) vs O(n). Redução de ~100ms para ~1ms para 1000 notas.

#### M004 — Economy service faz polling a cada 5s

**Arquivo:** `economyService.ts` (linhas 183-185)
**Risco:** MÉDIA
**Problema:** Polling a cada 5s faz 2+ requisições HTTP + scan de processos + verificação de idle.
**Impacto prático:** Dreno de bateria em laptop; cpu desnecessário.
**Afeta:** Usuários finais — ~0.5% CPU adicional constante.
**O que vai mudar:** Aumentar intervalo para 15-30s ou usar evento-driven (WebSocket).
**Ganho esperado:** Reduz tráfego de polling em 67-83%.

#### M005 — Listeners de janela acumulados em restart

**Arquivo:** `coreManager.ts` (linhas 86-98)
**Risco:** MÉDIA
**Problema:** `startEconomyService` attacha listeners `minimize`/`restore` na main window sem removê-los antes. Cada restart dobra os listeners.
**Impacto prático:** Memory leak. Cada restart adiciona mais handlers que disparam múltiplas vezes.
**Afeta:** Usuários finais — degradação gradual após vários restarts.
**O que vai mudar:** Remover listeners antes de readicionar.
**Ganho esperado:** Elimina memory leak.

### 3.4 Renderer (React / TypeScript)

#### R001 — Sem Error Boundary na raiz da aplicação

**Arquivo:** `apps/momai/src/renderer/src/main.tsx`
**Risco:** MÉDIA
**Problema:** Toda a aplicação renderiza sem um React Error Boundary. Um único erro não tratado em qualquer componente derruba toda a UI.
**Impacto prático:** Usuário vê tela branca em vez de mensagem de erro amigável.
**Afeta:** Usuários finais — perda de trabalho.
**O que vai mudar:** Adicionar `<ErrorBoundary>` em `App.tsx`.
**Ganho esperado:** Resiliência — erro em um componente não derruba o app inteiro.

#### R002 — Sem `AbortController` em chamadas de streaming

**Arquivo:** `useChatActions.ts` (linhas 111-408)
**Risco:** MÉDIA
**Problema:** `sendChatMessage` faz `fetch()` sem `AbortSignal`. Quando o usuário troca de thread ou envia nova mensagem, o stream antigo continua em background.
**Impacto prático:** Resource leak; respostas podem disparar dispatches para thread errada.
**Afeta:** Usuários finais — mensagens podem aparecer em conversa errada.
**O que vai mudar:** Criar `AbortController` por requisição e abortar ao iniciar nova.
**Ganho esperado:** Elimina resource leak e dispatches incorretos.

#### R003 — Array spreading redundante no reducer de chat

**Arquivo:** `chatReducer.ts` (linha 76)
**Risco:** MÉDIA
**Problema:** `action.updater` recebe `state.messages` e cria `[...prev]` a cada dispatch. No streaming de tokens (centenas por mensagem), são milhares de alocações de array.
**Impacto prático:** Pressão de GC durante streaming; eventuais frame drops.
**Afeta:** Usuários finais — jitter visual durante resposta longa.
**O que vai mudar:** Usar `concat` ou mutação controlada com `immer`.
**Ganho esperado:** Reduz alocações de array em ~90% durante streaming.

#### R004 — `any` generalizado (préload, API, componentes)

**Arquivos:** `services/api.ts`, `hooks/useChatHandlers.ts`, `MainViewRenderer.tsx`, `SkillResponseRegistry.ts`, etc.
**Risco:** MÉDIA
**Problema:** `window.api`, `window.momaiAPI` sem declaração de tipos. `env.d.ts` vazio além de referência Vite. Uso disseminado de `(window as any)`.
**Impacto prático:** TypeScript não consegue verificar chamadas de API do preload. Erros que poderiam ser captados em compile-time viram runtime errors.
**Afeta:** Desenvolvedores — perda de segurança de tipos.
**O que vai mudar:** Declarar tipos para a bridge do preload em `env.d.ts`.
**Ganho esperado:** Type safety nas chamadas IPC do renderer.

### 3.5 Node Core (Orquestração LLM)

#### N001 — `promptText` não inicializado se `promptRegistry` for nulo

**Arquivo:** `chat-service.js` (linhas 1191-1207)
**Risco:** ALTA
**Problema:** `promptText` é atribuído dentro de `if (promptRegistry && ...)` mas usado incondicionalmente depois. Se `promptRegistry` for nulo, `sanitizePromptText(undefined)` retorna `''` — prompt de sistema vazio.
**Impacto prático:** LLM recebe instrução de sistema vazia, produzindo respostas erráticas e sem personalidade.
**Afeta:** Usuários finais — qualidade de resposta degradada silenciosamente.
**O que vai mudar:** Adicionar fallback: `promptText = promptText || DEFAULT_SYSTEM_PROMPT`.
**Ganho esperado:** Garante prompt de sistema sempre presente.

#### N002 — Variáveis `toolSteps`/`activeSkill` redeclaradas (sombreadas)

**Arquivo:** `chat-service.js` (linhas 689-690 vs 1033-1034)
**Risco:** MÉDIA
**Problema:** `let toolSteps = []` e `let activeSkill = null` são declaradas no escopo da função (linhas 689-690) e redeclaradas dentro do bloco `try` (1033-1034). Hooks `beforeModel` (linhas 956-966) populam as variáveis externas, mas as internas é que são usadas na resposta final.
**Impacto prático:** Tool steps de hooks `beforeModel` são silenciosamente descartados. Skills que dependem disso (ex: busca web) têm seus passos perdidos.
**Afeta:** Usuários finais — steps de ferramentas sumindo da UI.
**O que vai mudar:** Remover as declarações internas (`let` duplicado).
**Ganho esperado:** Tool steps fluem corretamente para o frontend.

#### N003 — `catch {}` vazios no Node Core

**Arquivos:** `process-manager.js`, `websocket.js`, `extension-host-manager.js`, `extensions.routes.js`, `store.js`
**Risco:** MÉDIA
**Problema:** Dezenas de `catch {}` vazios engolem erros de operações de arquivo, rede, e gerenciamento de extensões.
**Impacto prático:** Falhas em instalação de extensão, escrita de store, e WebSocket são invisíveis.
**Afeta:** Desenvolvedores — impossível diagnosticar falhas.
**O que vai mudar:** Adicionar log de warning/error nos catches vazios.

#### N004 — `/settings` GET expõe objeto inteiro sem filtrar

**Arquivo:** `settings.routes.js` (linha 34)
**Risco:** MÉDIA
**Problema:** GET /settings retorna `store.settings` completo, incluindo `hardware_total_ram_gb`, `hardware_total_vram_gb` e campos internos. O filtro `filterToEditableSettings()` só é usado no PATCH.
**Impacto prático:** Dados de hardware e configuração interna expostos ao frontend.
**O que vai mudar:** Aplicar `filterToEditableSettings` também no GET.

#### N005 — `/extensions/events` público sem autenticação

**Arquivo:** `router.js` (linha 8)
**Risco:** MÉDIA
**Problema:** `PUBLIC_PATHS` inclui `/extensions/events` como rota não autenticada. Esse SSE stream pode conter dados sensíveis de extensões.
**Impacto prático:** Qualquer processo local pode escutar eventos de extensão.
**O que vai mudar:** Adicionar autenticação ao endpoint ou documentar intencionalidade.

### 3.6 Python Backend (Core)

#### P001 — Modelo Whisper carregado múltiplas vezes (OOM risk)

**Arquivos:** `voice.py` (linhas 282-300), `detector.py` (148-184), `voice.py` (97-125)
**Risco:** ALTA
**Problema:** Três caminhos de código diferentes podem carregar modelos Whisper independentes. No pior caso, 3 instâncias ocupam >3GB de RAM.
**Impacto prático:** OOM em sistemas com 8GB RAM ou menos. App trava.
**Afeta:** Usuários finais com hardware modesto.
**O que vai mudar:** Singleton factory em `app_state` que retorna instância única do modelo.
**Ganho esperado:** Reduz uso de RAM de ~3GB para ~1GB.

#### P002 — SQLite sem `check_same_thread=False` e sem WAL mode

**Arquivo:** `database/models.py` (linhas 59-63)
**Risco:** ALTA
**Problema:** SQLAlchemy engine sem `check_same_thread=False` e sem `PRAGMA journal_mode=WAL`. `SessionLocal()` é chamado de múltiplas threads.
**Impacto prático:** `ProgrammingError: SQLite objects created in a thread can only be used in that thread` em acesso concorrente.
**Afeta:** Usuários finais — erros aleatórios de banco.
**O que vai mudar:** Adicionar `check_same_thread=False`, `poolclass=NullPool`, e executar PRAGMA WAL.
**Ganho esperado:** Elimina erro de thread em SQLite.

#### P003 — WebSocket sem proteção de thread na lista de conexões

**Arquivo:** `voice.py` (linhas 15-36), `app_state.py` (166-181)
**Risco:** ALTA
**Problema:** `active_websockets` é uma `list` acessada de múltiplas threads sem lock. `broadcast_to_sockets` itera e modifica concorrentemente.
**Impacto prático:** Corrupção de lista — crash, broadcast perdido, ou conexões zumbis.
**Afeta:** Usuários finais — voice pipeline instável.
**O que vai mudar:** Substituir por `list` + `threading.Lock` ou usar estrutura thread-safe.
**Ganho esperado:** Elimina race condition.

#### P004 — Chamadas síncronas bloqueantes em rotas async

**Arquivo:** `voice.py` (linhas 128-145)
**Risco:** ALTA
**Problema:** `/quick-transcribe` é `def` síncrono (não `async`) que bloqueia por até 30s (gravação de áudio + inferência Whisper). Bloqueia worker thread do FastAPI.
**Impacto prático:** Sob carga concorrente, todas as threads do pool são esgotadas — server responde com 503.
**Afeta:** Usuários finais — server fica indisponível.
**O que vai mudar:** Converter para `async def` e usar `asyncio.to_thread()` para operação blocking.
**Ganho esperado:** Server continua responsivo durante transcrição longa.

#### P005 — `sanitize_message()` definida, testada, mas nunca usada

**Arquivo:** `error_handler.py` (linhas 32-35), `tests/test_error_sanitization.py`
**Risco:** MÉDIA
**Problema:** Função de sanitização de erros implementada e com testes, mas nunca importada por middleware, rota, ou exception handler.
**Impacto prático:** Erros retornam detalhes internos (stack traces, paths) para o cliente. 35 linhas de dead code.
**Afeta:** Usuários finais — vazamento de informação em erros.
**O que vai mudar:** Remover função morta ou conectá-la ao global exception handler.
**Ganho esperado:** Sanitização real de erros ou código limpo.

#### P006 — Migrations ad-hoc sem version tracking

**Arquivo:** `database/models.py` (linhas 70-142)
**Risco:** MÉDIA
**Problema:** `init_db()` executa `ALTER TABLE` baseado em inspeção de colunas. Sem version tracking, não distingue "coluna não existe" de "coluna foi renomeada".
**Impacto prático:** Schema corruption em upgrades futuros com mudanças estruturais.
**Afeta:** Desenvolvedores — risco em releases.
**O que vai mudar:** Implementar migration versionada (Alembic) ou manter ad-hoc mas com versionamento.
**Ganho esperado:** Migrations seguras e rastreáveis.

### 3.7 Configuração & Build

#### C001 — Nenhum pipeline CI/CD

**Arquivo:** `.github/workflows/` — ausente
**Risco:** MÉDIA
**Problema:** Zero automação de CI/CD. Sem testes automatizados, build verification, ou security scanning.
**Impacto prático:** Toda release é manual. Regressões só são descobertas tarde.
**Afeta:** Organização — risco de quebrar produção.
**O que vai mudar:** Adicionar workflows GitHub Actions para lint, typecheck, test, build.
**Ganho esperado:** Quality gate automático.

#### C002 — ESLint com regras críticas desabilitadas

**Arquivo:** `apps/momai/eslint.config.mjs` (linhas 29-42)
**Risco:** MÉDIA
**Problema:** `@typescript-eslint/no-explicit-any`, `react-hooks/exhaustive-deps`, `no-unused-vars`, `no-empty` estão OFF.
**Impacto prático:** TypeScript não oferece segurança real de tipos. Hooks com deps faltando não são detectados.
**Afeta:** Desenvolvedores — bugs evitáveis passam despercebidos.
**O que vai mudar:** Reativar gradualmente as regras começando por `no-explicit-any` e `exhaustive-deps`.
**Ganho esperado:** Type safety + correção de hooks.

#### C003 — `npmRebuild: false` para módulos nativos

**Arquivo:** `apps/momai/electron-builder.yml` (linha 158)
**Risco:** MÉDIA
**Problema:** Módulos nativos não são recompilados para o ABI do Electron. Podem crashar em runtime se os binários pré-compilados não baterem.
**Impacto prático:** Crash em produção em módulos como `onnxruntime`, `ctranslate2`.
**Afeta:** Usuários finais — instabilidade.
**O que vai mudar:** Ativar `npmRebuild` ou documentar por que está desligado.

#### C004 — Docker rodando como root

**Arquivo:** `scripts/Dockerfile.linux`
**Risco:** MÉDIA
**Problema:** Sem diretiva `USER`. Container roda como root.
**Impacto prático:** Qualquer passo de build comprometido tem acesso root.
**Afeta:** Infraestrutura.
**O que vai mudar:** Adicionar `USER node` após instalação de dependências.
