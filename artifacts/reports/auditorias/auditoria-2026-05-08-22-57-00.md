## 1. Resumo Executivo

A auditoria completa do MomAIOS revelou **59 problemas** no total, sendo **2 críticos**, **21 de alta prioridade**, **29 de média prioridade** e **7 de baixa prioridade**. As áreas mais problemáticas são:

- **Segurança**: Injeção de comandos via `exec()` no sistema de extensões e launcher
- **Duplicação de código**: Cópias quase idênticas de arquivos grandes (node-core, launcher runtime, detectores de idioma)
- **TypeScript sem tipo**: Uso generalizado de `any`, `@ts-ignore`, e falta de declarações para a bridge Electron
- **Performance**: Scans completos de filesystem, operações síncronas em hot paths, FFT em threads de áudio
- **Streaming SSE**: Mensagens `{done: true}` não enviadas em casos de abort, erros que não interrompem o fluxo
- **Práticas assíncronas**: Race conditions em `active_websockets`, variáveis de módulo compartilhadas sem sincronização

## 2. Problemas Críticos

### C1. Injeção de Comando no Launcher Skill (`openItem`)

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `apps/momai/scripts/skills/packaged/launcher/runtime.js:670` |
| **Risco** | **CRÍTICO** - Execução remota de código arbitrário |

**O problema:** O método `openItem()` constrói um comando shell usando template strings e `exec()`:
```js
const cmd = process.platform === 'win32'
  ? `start "" "${normalized}"`
  : `open "${normalized}"`
exec(cmd, (err) => { ... })
```
O caminho `normalized` é verificado apenas com `fs.existsSync()` (linha 667), sem qualquer sanitização contra caracteres shell como `&`, `|`, `` ` ``, `$()`. O caminho origina-se da resposta do LLM (via `search_local_items`), tornando este um vetor de injeção crítico. Uma cópia idêntica existe em `data/extensions/launcher/runtime.js:~670`.

**Impacto prático:** Um usuário mal-intencionado poderia solicitar ao assistente "abra a pasta downloads" e, se o LLM produzir um caminho malicioso ou se um arquivo com nome malicioso estiver no filesystem, comandos arbitrários seriam executados no computador do usuário.

**O que está afetando:** Usuários finais - qualquer comando executado no contexto do processo Node Core.

**O que vai mudar:** Substituir `exec()` por `child_process.spawn()` ou `execFile()` com argumentos em array, eliminando o parsing de shell.

**Ganho esperado:** Eliminação completa do vetor de injeção de comandos.

**Soluções possíveis:**
1. (Recomendada) Substituir `exec()` por `child_process.spawn()` ou `execFile()` com array de argumentos
2. Escapar rigorosamente todos os caracteres shell no caminho
3. Validar o caminho contra uma lista de permissão (allowlist) de diretórios conhecidos

**Solução recomendada:** Opção 1 - usar `spawn()` ou `execFile()` com array elimina a necessidade de escaping shell e é a abordagem mais segura e de manutenção mais simples. Combinar com validação allowlist de diretórios para defesa em profundidade.

### C2. Injeção de Comando na Instalação de Extensões (`extractZip`)

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `apps/momai/scripts/node-core/api/routes/extensions.routes.js:86-100` |
| **Risco** | **CRÍTICO** - Execução remota de código |

**O problema:** A extração de ZIPs de extensões usa `exec()` com PowerShell:
```js
exec(`powershell -NoProfile -Command "Expand-Archive -Path '${zipPath.replace(/'/g, "''")}' -DestinationPath '${destDir.replace(/'/g, "''")}' -Force"`)
```
Apenas aspas simples são escapadas. PowerShell pode executar comandos injetados via `;`, `|`, `$(...)`, backticks, etc. O `zipPath` e `destDir` são derivados do `payload.id` da extensão, que vem da requisição do cliente.

**Impacto prático:** Instalar uma extensão maliciosa do store poderia executar comandos arbitrários no sistema do usuário.

**O que está afetando:** Usuários que instalam extensões.

**O que vai mudar:** Substituir comando PowerShell por API nativa de extração de ZIP do Node.js (`adm-zip` ou `unzipper`), ou usar `child_process.spawn()` com `Expand-Archive` em argumentos.

**Ganho esperado:** Eliminação completa do vetor de injeção.

**Soluções possíveis:**
1. (Recomendada) Usar biblioteca JavaScript nativa (ex: `adm-zip`) para extração - sem shell envolvido
2. Usar `spawn('powershell', ['-NoProfile', '-Command', 'Expand-Archive', ...])` com array de argumentos
3. Manter `exec()` mas escapar rigorosamente todos os metacaracteres PowerShell (frágil e propenso a erros)

**Solução recomendada:** Opção 1 - eliminar completamente a dependência de shell para extração ZIP usando uma biblioteca pura JavaScript.

## 3. Problemas de Alta Prioridade

### H1. XSS via iframe srcdoc com allow-scripts

| Campo | Detalhe |
|-------|---------|
| **Arquivos** | `components/chat/DevHtmlRenderCard.tsx:47-50`, `components/chat/HtmlPreviewCard.tsx:24-29` |
| **Risco** | **ALTO** - Cross-Site Scripting |

**O problema:** Ambos os componentes injetam HTML bruto em `iframe srcdoc` com `sandbox="allow-scripts allow-forms allow-modals"`. O token `allow-scripts` permite execução arbitrária de JavaScript. Embora `allow-same-origin` não esteja presente (bloqueando acesso à origem), scripts ainda podem ser executados, permitindo phishing, confusão visual do usuário e ataques de engenharia social.

**Soluções possíveis:**
1. (Recomendada) Remover `allow-scripts` - usar apenas renderização estática. Se scripts forem necessários, isolar em um processo separado.
2. Sanitizar rigorosamente o HTML antes de injetar (usar DOMPurify).
3. Implementar um sandbox via WebWorker ou página separada com comunicação postMessage limitada.

---

### H2. Extensão Host Worker sem Isolamento VM

| Campo | Detalhe |
|-------|---------|
| **Arquivos** | `apps/momai/scripts/node-core/services/extension-host-worker.js`, `apps/momai/scripts/skills/registry.js:436-497` |
| **Risco** | **ALTO** - Escapamento de sandbox |

**O problema:** O host worker carrega extensões via `import()` dinâmico **sem nenhum isolamento VM**. A runtime.js da extensão tem acesso total a `fs`, `child_process`, `process.env`, `require()`, e rede. O objeto `momai` exposto como bridge tem apenas `log()`. As verificações de permissão no `registry.js` são puramente consultivas (advisory) - verificam `allowed === false` mas **nunca aplicam** que o host worker realmente bloqueie essas capacidades.

**Soluções possíveis:**
1. (Recomendada) Usar `vm.Script` ou `vm.createContext()` do Node.js para criar um contexto isolado com apenas as APIs explicitamente permitidas.
2. Implementar renderização de permissões no nível do worker - o worker não deve ter acesso a `require('child_process')` ou `require('fs')` a menos que explicitamente autorizado.
3. Usar sub-processo separado com IPC limitado para execução de extensões.

### H3. Falta de Declarações de Tipo para Bridge Electron

| Campos | Detalhes |
|--------|----------|
| **Arquivos** | ~14 ocorrências: `hooks/useStatus.ts:175`, `hooks/useAppInitialization.ts:50-51`, `hooks/usePythonStatus.ts:12`, `hooks/useWindowMaximized.ts:8-9` e outros |
| **Risco** | **ALTO** - Perda total de type safety na camada IPC |

**O problema:** `window.api` e `window.electron.ipcRenderer` são acessados com `@ts-ignore` em ~14 locais diferentes. Não há declarações de tipo para `window.api` em lugar nenhum do renderer. O arquivo `env.d.ts` contém apenas `/// <reference types="vite/client" />`. Toda a bridge Electron é completamente sem tipo.

**Impacto prático:** Qualquer mudança nos nomes dos métodos IPC ou nos parâmetros não é detectada em tempo de compilação. Erros só aparecem em runtime. Desenvolvedores precisam caçar manualmente as chamadas correspondentes.

**Soluções possíveis:**
1. (Recomendada) Criar um arquivo `types/api.d.ts` com declarações completas de tipo para `window.api` e `window.electron`.
2. Usar `type-only import/export` para compartilhar tipos entre preload e renderer.
3. Gerar tipos automaticamente a partir dos handlers IPC.

### H4. Sandbox Desabilitado sem documentação

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `src/main/windowManager.ts:234-249` + `188-203` |
| **Risco** | **ALTO** - Superfície de ataque expandida |

**O problema:** Ambas as janelas (principal e overlay) têm `sandbox: false`. `contextIsolation`, `nodeIntegration` e `webSecurity` não são definidos explicitamente (dependentes de defaults do Electron). A ausência de definições explícitas torna o código vulnerável a mudanças de defaults em futuras versões do Electron.

**Soluções possíveis:**
1. (Recomendada) Definir explicitamente todas as flags de segurança: `contextIsolation: true`, `nodeIntegration: false`, `webSecurity: true`. Se sandbox precisar ficar false, documentar o porquê.
2. Avaliar se o sandbox pode ser ativado (pode exigir reestruturação do preload).

### H5. Race Condition em active_websockets

| Campo | Detalhe |
|-------|---------|
| **Arquivos** | `apps/core/app_state.py:14`, `apps/core/api/routes/voice.py:17` |
| **Risco** | **ALTO** - Crash sob concorrência |

**O problema:** `active_websockets` é uma `list[WebSocket]` simples. Múltiplas conexões WebSocket concorrentes chamam `append(ws)` (voice.py:17) e `broadcast_to_sockets` (app_state.py:161) itera a lista enquanto `remove()` pode ocorrer em error handlers (voice.py:24-25, app_state.py:171). Não há `asyncio.Lock` ou estrutura thread-safe.

**Soluções possíveis:**
1. (Recomendada) Usar `asyncio.Lock` em todas as mutações da lista.
2. Usar `set[WebSocket]` com operações thread-safe.
3. Usar `asyncio.Queue` para operações de broadcast.

### H14. FFT em Audio Thread (detector)

| Campo | Detalhe |
|-------|---------|
| **Arquivo** | `apps/core/services/voice/detector.py:227-239` |
| **Risco** | **ALTO** - Glitches de áudio |

**O problema:** A cada ~250ms, para cada chunk de áudio, `np.abs(np.fft.rfft(sc))` é computado no callback de áudio em tempo real do sounddevice, que é uma thread crítica. Operações NumPy aqui podem causar glitches de áudio.

**Soluções possíveis:**
1. (Recomendada) Mover FFT para uma thread separada com uma fila (queue).
2. Reduzir a frequência do cálculo.
3. Usar uma implementação FFT mais leve em pure Python ou C.
